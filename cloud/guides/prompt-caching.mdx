NEAR AI Cloud automatically caches prompt prefixes for every supported model — no API changes or opt-in flags required. When a request shares a prefix with a previous request to the same model, the cached portion is reused from the in-TEE KV cache and billed at a discounted cache-read rate rather than the full input rate.

## How It Works

<Steps>
  <Step title="KV cache stored inside the TEE">
    After the first request, the key–value activations for the prompt prefix are stored in the model's TEE-isolated KV cache. The cache is scoped to the model deployment and never shared across organizations.
  </Step>
  <Step title="Cached prefix reused on subsequent requests">
    When a new request arrives with a matching prefix, the model skips recomputation for the cached portion and continues from the cached state. The longer the shared prefix, the greater the savings.
  </Step>
  <Step title="Billed at the cache-read rate">
    Tokens served from the cache are billed at the discounted cache-read price rather than the full input token price. You can find per-model cache-read pricing on the [Models](/cloud/models) page or by calling `GET /v1/models`.
  </Step>
</Steps>

## Tracking Cache Hits

Both the Chat Completions API and the Responses API return token-level detail that shows how many tokens were served from cache.

**Chat Completions** — check `usage.prompt_tokens_details.cached_tokens`:

```json
{
  "id": "chatcmpl-abc123",
  "object": "chat.completion",
  "model": "zai-org/GLM-5.1-FP8",
  "choices": [...],
  "usage": {
    "prompt_tokens": 1024,
    "completion_tokens": 128,
    "total_tokens": 1152,
    "prompt_tokens_details": {
      "cached_tokens": 896
    }
  }
}
```

**Responses API** — check `usage.input_tokens_details.cached_tokens`:

```json
{
  "id": "resp-xyz789",
  "object": "response",
  "model": "zai-org/GLM-5.1-FP8",
  "output": [...],
  "usage": {
    "input_tokens": 1024,
    "output_tokens": 128,
    "total_tokens": 1152,
    "input_tokens_details": {
      "cached_tokens": 896
    }
  }
}
```

A `cached_tokens` value of `0` means the request was a cache miss (the first request for that prefix, or the prefix changed).

## Getting the Most Out of the Cache

1. **Put stable content first.** Place system prompts, static instructions, and reference documents at the beginning of the prompt, before any per-request variable content such as the user's message. Caching works on prefixes, so only the leading portion of the prompt can be reused.

2. **Keep prefixes byte-identical.** Even a single character difference — including whitespace, capitalization, or punctuation — will break the prefix match and result in a cache miss. Render system prompts from a template and avoid any dynamic injection into the stable prefix.

3. **Short prompts may not be cached.** Very short prompts (typically under a few hundred tokens) may not benefit from caching, as the overhead of cache lookup is not warranted. Caching provides the most benefit on large, repeated prefixes such as long system prompts, few-shot examples, or document chunks.

4. **Cache is per model deployment.** The KV cache is maintained per model. Switching the `model` field to a different model identifier — even a different quantization of the same base model — results in a cache miss on the first request.

<Note>
  The KV cache is fully isolated inside the TEE. Cached prompt activations never leave the secure enclave and are not accessible to any operator, including NEAR AI. Cache data from one organization is never reused for another organization's requests.
</Note>
