To verify a NEAR AI model is operating in a secure trusted environment, there are two main steps:

1. [Request a Model Attestation](#request-model-attestation) report from NEAR AI Cloud
2. [Verify the Model Attestation](#verifying-model-attestation) report using NVIDIA and Intel attestation authenticators

<Tip>
See an easy-to-follow example implementation in the [NEAR AI Cloud Verification Example](https://github.com/near-examples/nearai-cloud-verification-example) repo.

A more complete verifier implementation is available in the [NEAR AI Cloud Verifier](https://github.com/nearai/nearai-cloud-verifier) repo.
</Tip>

## Request Model Attestation

To request a model attestation from NEAR AI Cloud, use one of the following `GET` API endpoints:

**Via Gateway:**
```text
https://cloud-api.near.ai/v1/attestation/report?model={model_name}&signing_algo=ecdsa&nonce={nonce}
```

**Via Direct Completions:**
```text
https://{slug}.completions.near.ai/v1/attestation/report?signing_algo=ecdsa&nonce={nonce}
```

The `signing_algo` parameter specifies the signing algorithm used (`ecdsa` or `ed25519`). The `nonce` parameter is optional but recommended — it should be a randomly generated 64-character hexadecimal string (32 bytes) that ensures attestation freshness and prevents replay attacks. If not provided, the server will generate one for you.

The gateway endpoint requires an API key (`Authorization: Bearer <api-key>`); report retrieval is free and never counts against your usage. The direct completions endpoint is served by the model TEE itself and needs no API key.

With direct completions, you can also pass `include_tls_fingerprint=true` to bind the TLS certificate fingerprint to the attestation report. This is disabled by default for compatibility with existing clients. Without the flag, `report_data` binds only the signing key and nonce. With the flag, `report_data[0:32]` becomes `SHA256(signing_address || tls_cert_fingerprint)`, which lets you verify that the HTTPS connection terminates inside the model TEE. See [TLS Attestation Verification](/cloud/verification/tls).

  -H 'Authorization: Bearer <YOUR-NEAR-AI-CLOUD-API-KEY>'

### Example Response

```json
{
  "model_attestations": [       // List of all GPU nodes in the network
    {
      "signing_address": "...", // TEE Public Key
      "nvidia_payload": "...",  // Attestation report used to verify w/ NVIDIA
      "intel_quote": "..."      // Attestation report used to verify w/ Intel
    }
  ]
}
```

- **`model_attestations`** — A list of attestations from all GPU nodes. Multiple TEE nodes may serve inference requests, so you may receive more than one entry.
- **`signing_address`** — The account address generated inside the TEE that will be used to sign chat responses. Use the `signing_address` from `model_attestations` to select the appropriate TEE node when verifying its integrity.
- **`nvidia_payload`** and **`intel_quote`** — Attestation reports formatted for NVIDIA TEE and Intel TEE respectively, used to verify the integrity of the TEE. See [Verifying Model Attestation](#verifying-model-attestation) for details.

<Note>
**Implementation:** This endpoint is defined in the [NEAR AI Private ML SDK](https://github.com/nearai/private-ml-sdk/blob/a23fa797dfd7e676fba08cba68471b51ac9a13d9/vllm-proxy/src/app/api/v1/openai.py#L170).
</Note>

## Verifying Model Attestation

Once you have [requested a model attestation](#request-model-attestation), you can use the returned payload to verify its authenticity. You can verify:

- **GPU attestation** — Submit the GPU evidence payload to NVIDIA NRAS and verify the nonce matches
- **Intel TDX quote** — Verify the TDX quote with the [`dcap-qvl`](https://github.com/Phala-Network/dcap-qvl) library
- **TDX report data** — Validate that report data binds the signing key (ECDSA or Ed25519) and nonce
- **Compose manifest** — Display the Docker Compose manifest and verify it matches the `mr_config` measurement

### Verify GPU Attestation

NVIDIA offers a [Remote Attestation Service (NRAS)](https://docs.nvidia.com/attestation/cloud-services/latest/nras/nras_introduction.html) that allows you to verify you are using a trusted environment with one of their GPUs. To verify:

1. Submit the GPU evidence payload (`nvidia_payload`) to NVIDIA NRAS.
2. Verify the nonce in the GPU payload matches the request nonce.
3. Validate the NVIDIA attestation verdict is PASS.

The `nvidia_payload` contains:

- `nonce` — The nonce from your attestation request
- `arch` — Architecture of the GPU (`HOPPER` or `BLACKWELL`)
- `evidence_list` — A list of GPU evidence items, each containing evidence and a corresponding certificate

The `evidence_list` contains Base64-encoded data listing the GPU's hardware identity, firmware and software measurements, security configuration state, and endorsement certificates (signed measurements from the GPU's unique key). NVIDIA burns this unique private key into each GPU during manufacturing and retains only the corresponding public key, which is used to verify the authenticity of attestations.

Submit the `nvidia_payload` JSON object directly to the NVIDIA NRAS endpoint:

```bash
curl -X POST https://nras.attestation.nvidia.com/v3/attest/gpu \
  -H "accept: application/json" \
  -H "content-type: application/json" \
  -d "<NVIDIA_PAYLOAD_FROM_NEARAI_MODEL_ATTESTATION>"
```

See the official NVIDIA documentation: [https://docs.api.nvidia.com/attestation/reference/attestmultigpu_1](https://docs.api.nvidia.com/attestation/reference/attestmultigpu_1)

<Tip>
NVIDIA's attestation verification response returns an "Entity Attestation Token" (EAT) encoded as a JSON Web Token (JWT). To decode these values, use an online tool such as [jwt.io](https://jwt.io) or a library such as [jose](https://www.npmjs.com/package/jose).

The key fields to check in the decoded JWT are:
- `x-nvidia-overall-att-result: true` — The overall attestation passed
- `eat_nonce` — Must match the nonce you supplied in the request
- `x-nvidia-gpu-attestation-report-nonce-match: true` — Confirms nonce freshness
- `secboot: true` — Confirms secure boot is enabled
- `dbgstat: "disabled"` — Confirms debug mode is disabled
</Tip>

### Verify TDX Quote

You can verify the Intel TDX quote using the value of `intel_quote` with the [`dcap-qvl`](https://github.com/Phala-Network/dcap-qvl) library. This verifies:

- The CPU TEE measurements are valid
- The quote is authentic and signed by Intel
- The TEE environment is genuine

Alternatively, you can verify the Intel TDX quote at the [TEE Attestation Explorer](https://proof.t16z.com/).

### Verify TDX Report Data

The TDX report data validates that:

- The report data binds the signing address (ECDSA or Ed25519)
- The report data embeds the request nonce

This ensures cryptographic binding between the signing address and the hardware, and prevents replay attacks through nonce freshness.

### Verify Compose Manifest

The attestation response includes Docker Compose manifest information in the `info` field. To verify:

1. Extract the Docker Compose manifest from the attestation.
2. Calculate the SHA-256 hash of the compose manifest.
3. Compare it with the `mr_config` measurement from the verified TDX quote.
4. Verify they match, proving the exact container configuration running inside the TEE.

This ensures the exact Docker Compose file is deployed to the TEE environment.
