---
title: "TLS Connection Binding"
description: "Bind a live NEAR AI Cloud gateway TLS connection to the gateway attestation."
---

TLS binding checks that the HTTPS peer you are connected to matches the identity authenticated by [Gateway attestation](/cloud/verification/cloud-api/gateway-attestation). It connects the environment evidence to the connection carrying your request.

The Python, Rust, and Go [Gateway inference clients](/cloud/verification/verify-with-sdk) enable TLS binding by default, as does the JavaScript client imported from `@nearai/inference-sdk/node`. They get the Gateway report before sending credentials, then pin model metadata, model reports, inference requests, and receipt lookups to the verified Gateway public key.

<Warning>
  Obtain the peer certificate and Gateway report on the **same TLS connection**. On later connections, check the pin before sending credentials or request data.
</Warning>

<Note>
  Use a server-side SDK for Gateway TLS binding. Browser Fetch APIs do not expose the peer certificate or its SPKI.
</Note>

## What this checks

When you request `include_tls_fingerprint=true`, `gateway_attestation.tls_cert_fingerprint` is the SHA-256 hash of the gateway certificate's SubjectPublicKeyInfo (SPKI). The verified quote binds that fingerprint, the gateway signing identity, and the nonce.

## Verification flow

1. Generate a fresh 32-byte nonce in the client.
2. Open a TLS connection to `cloud-api.near.ai` using the trust configuration required by your application.
3. Read the peer certificate from that connection and calculate `SHA-256(SPKI_DER)`.
4. Reuse the same open connection to request `/v1/attestation/report` with `include_tls_fingerprint=true`, the nonce, and the signing algorithm you require. Do not send an API key: the gateway report needs none, so no credential crosses the connection before you have verified it.
5. Verify `gateway_attestation.intel_quote`, then check the nonce, gateway signer, and TLS-fingerprint binding in the verified quote.
6. Compare the calculated peer SPKI hash with `gateway_attestation.tls_cert_fingerprint`.

Calculate the peer SPKI hash from the certificate observed on the live connection, rather than the optional `tls_certificate` response field.

Reuse that connection, or configure your HTTPS transport to check the verified SPKI on each new connection. Use that transport for model metadata, model attestations, inference, and response signatures. A standalone evidence client also needs to use the pinned transport for its authenticated calls.

## Required handling

| Result | Action when TLS endpoint binding is required |
| --- | --- |
| `gateway_attestation.tls_cert_fingerprint` is absent | Treat TLS binding as unavailable. Request a new report with `include_tls_fingerprint=true`. |
| Peer SPKI hash differs | Reject the connection. Fetch and verify a fresh Gateway report before accepting a new key. |
| Quote, nonce, or signer binding fails | Reject the report and fetch fresh evidence. |
| Certificate and report came from different connections | Treat the result as inconclusive. |

Fetch new evidence when the Gateway key changes or the evidence reaches your policy's maximum age.

## Continue the flow

After preflight, send inference through the verified connection and check the [response signature](/cloud/verification/cloud-api/response-signatures) against the retained evidence. Return to the [overview](/cloud/verification) for the full flow or [troubleshooting](/cloud/verification/troubleshooting) if connection binding is unavailable.
