Before sending a prompt, the SDK checks the NEAR model service's hardware evidence. The evidence you need for each check depends on what you want to verify.

| What you want to verify | Evidence to use |
| --- | --- |
| **Model service** | Hardware attestation authenticates the NEAR service's deployment measurements and signing key. Use that key to verify a [signed reply](/cloud/verification/cloud-api/response-signatures). |
| **Proxy or inference engine image** | An optional [image provenance policy](/cloud/verification/cloud-api/image-provenance) checks each image you select. For example, `nearaidev/vllm-proxy-rs` selects the proxy. Add the engine image to check its build too. |
| **Model weights** | Weights loaded separately by the engine require evidence of their digest and a link between those weights and the running service. |

The [SDK tutorial](/cloud/verification/verify-with-sdk) shows the application flow. The manual steps below request NEAR evidence explicitly with `provider=near`; support for other provider formats is separate.

## Request model evidence

Request the canonical model ID with `x-no-aliasing: true` to require an exact model match. Reports for publicly listed models are available without an API key. For an unlisted model enabled for your organization, include `Authorization: Bearer <YOUR_NEAR_AI_CLOUD_API_KEY>`.

```bash
NONCE="$(openssl rand -hex 32)"

curl --fail-with-body -G 'https://cloud-api.near.ai/v1/attestation/report' \
  --data-urlencode 'model=z-ai/glm-5.3-flash' \
  --data-urlencode 'provider=near' \
  --data-urlencode 'include_tls_fingerprint=false' \
  --data-urlencode 'signing_algo=ecdsa' \
  --data-urlencode "nonce=${NONCE}" \
  -H 'Accept: application/json' \
  -H 'x-no-aliasing: true'
```

The response includes gateway evidence and NEAR model-report candidates in `model_attestations[]`. The field is omitted when no candidate is available. If your policy requires NEAR model evidence, reject a missing or empty `model_attestations[]`. Before sending a completion, verify every candidate and retain the verified results.

For Chat Completions, the SDK selects a verified model public key and sends it in `X-Model-Pub-Key`. Keep the signing identity from that report with the request. A later `provider_tee` receipt must match that identity.

`provider=near` selects the source of reports for this attestation request. The later completion follows its own provider routing.

## NEAR model report fields

The NEAR report uses these fields:

| Field | Purpose |
| --- | --- |
| `intel_quote` | Intel TDX evidence. |
| `event_log` | Runtime measurement log. Replay it and match the result to the quote's RTMR3. |
| `request_nonce` | Echoed request nonce. Require it to match the client nonce, then confirm the nonce binding from the verified quote. |
| `report_data` | Not currently returned in model reports. Read report data from the verified quote. |
| `signing_address` and `signing_algo` | Model signing identity and its algorithm. |
| `signing_public_key` | Model public key used by the E2EE flow. With `signing_algo=ed25519` it is the Ed25519 key for the default E2EE flow; with `ecdsa` it is the secp256k1 key for ECDSA E2EE. |
| `nvidia_payload` | NVIDIA GPU evidence, when present. |
| `info.tcb_info.app_compose` | Raw measured configuration string. Hash it and match it to the quote's MRCONFIGID. `tcb_info` can itself be JSON text. |

## Verify NEAR model reports

Perform these checks on every returned candidate before sending a completion:

1. Verify `intel_quote` with an Intel DCAP quote verifier, such as [`dcap-qvl`](https://github.com/Phala-Network/dcap-qvl), and apply your TCB and advisory policy.
2. Read report data from the verified quote. Require it to bind the client-generated nonce and `signing_address`; require `request_nonce` to match the client nonce. When `report_data` is present, require it to match the verified quote. Interpret the address using `signing_algo`.
3. Replay `event_log` as described in [Replay the RTMR3 event log](/cloud/verification/reference/quote-nonce-signer#replay-the-rtmr3-event-log) and require the resulting RTMR3 to equal the RTMR3 in the verified quote.
4. If `tcb_info` is JSON text, decode it to obtain `app_compose`. Hash the raw `app_compose` string without parsing or reserializing it. Require the quote's 48-byte MRCONFIGID to equal `01`, then that SHA-256 hash, then 15 zero bytes. See [Check the configuration measurement](/cloud/verification/reference/quote-nonce-signer#check-the-configuration-measurement).
5. When GPU evidence is present, follow [GPU evidence verification](/cloud/verification/reference/quote-nonce-signer#verify-gpu-evidence-when-present).
6. Apply your own allowlist and provenance policy to the verified measurements.

## Relationship to NEAR AI Cloud gateway TLS

The browser or client connection is to `cloud-api.near.ai`. Verify its TLS endpoint binding against `gateway_attestation`. See [NEAR AI Cloud gateway TLS connection binding](/cloud/verification/cloud-api/tls).

## Verify a signed response

For a `provider_tee` receipt, the SDK verifies the signature and exact bytes against the signer selected for the request. The result includes every previously verified model report with that signing address and algorithm. A `gateway` receipt uses the previously verified Gateway signing key. See [response signatures](/cloud/verification/cloud-api/response-signatures).
