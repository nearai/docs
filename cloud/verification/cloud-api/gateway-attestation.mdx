---
title: "Gateway Attestation"
description: "Verify the NEAR AI Cloud gateway attestation for requests sent to cloud-api.near.ai."
---

`gateway_attestation` authenticates the Gateway environment and its signing identity. Verify it before sending inference so that a later response signature can be checked against an identity you already verified. Model environments have [separate evidence](/cloud/verification/cloud-api/model-attestations).

For application integration, start with [Verify with the SDK](/cloud/verification/verify-with-sdk). The SDK performs Gateway verification during preflight and can reuse a verified session within its configured cache lifetime. The steps below explain the underlying manual checks.

## Request gateway evidence

Generate the nonce in your client. It must be 32 random bytes encoded as 64 hexadecimal characters. Fetch the Gateway report without credentials. If the endpoint returns `429`, wait for the `Retry-After` delay before trying again.

```bash
NONCE="$(openssl rand -hex 32)"

curl --fail-with-body -G 'https://cloud-api.near.ai/v1/attestation/report' \
  --data-urlencode 'signing_algo=ecdsa' \
  --data-urlencode "nonce=${NONCE}" \
  -H 'Accept: application/json'
```

The response contains the gateway report at `gateway_attestation`. For a deployment-first completion, verify and retain it before sending the completion. Add `model=<MODEL_ID>`, `provider=near`, and the `x-no-aliasing: true` header when you also need [NEAR model evidence](/cloud/verification/cloud-api/model-attestations). That request returns NEAR model reports in `model_attestations[]`; verify every entry before sending the completion. Add `include_tls_fingerprint=true` only when you are following the [NEAR AI Cloud gateway TLS flow](/cloud/verification/cloud-api/tls).

## Verify the gateway report

For `gateway_attestation`:

1. Verify `intel_quote` with an Intel DCAP quote verifier, such as [`dcap-qvl`](https://github.com/Phala-Network/dcap-qvl), and apply your TCB and advisory policy.
2. Read `report_data` and measurements from the **verified quote**. Compare the HTTP response's `request_nonce` and `report_data` with the nonce and report data you verified; reject missing or mismatched values.
3. Check that the verified quote binds the nonce generated by your client and the reported `signing_address`. Use `signing_algo` to interpret that identity and verify response signatures.
4. Replay `event_log` as described in [Replay the RTMR3 event log](/cloud/verification/reference/quote-nonce-signer#replay-the-rtmr3-event-log) and require the result to equal the RTMR3 in the verified quote.
5. Obtain the raw `info.tcb_info.app_compose` string. If `tcb_info` is JSON text, decode it first. Hash `app_compose` without parsing or reserializing it, and require the quote's 48-byte MRCONFIGID to equal `01`, then that SHA-256 hash, then 15 zero bytes. See [Check the configuration measurement](/cloud/verification/reference/quote-nonce-signer#check-the-configuration-measurement).
6. When a TLS fingerprint was requested, verify its binding as part of the [NEAR AI Cloud gateway TLS flow](/cloud/verification/cloud-api/tls).
7. Apply your accepted measurement and image-provenance policy.

## Field scope

| Field path | What it describes |
| --- | --- |
| `gateway_attestation.intel_quote` | The gateway's Intel TDX quote. |
| `gateway_attestation.event_log` | Runtime measurement log. Replay it against the quote's RTMR3. |
| `gateway_attestation.request_nonce` and `.report_data` | HTTP copies to compare with the client nonce and verified quote. |
| `gateway_attestation.signing_address` and `.signing_algo` | The gateway signing identity and algorithm. |
| `gateway_attestation.tls_cert_fingerprint` | The gateway TLS binding when requested. |
| `gateway_attestation.info.tcb_info.app_compose` | Raw measured configuration string. Hash it and match it to the quote's MRCONFIGID. |
| `model_attestations[]` | Separate NEAR model-evidence candidates when requested with `model` and `provider=near`. Verify every candidate separately. |

## Freshness and failure handling

Check freshness by matching the nonce in the verified quote to the nonce your client generated and retained. If the report is unavailable, the quote fails, the nonce does not match, or the identity does not match, treat the gateway property as unverified.

For a deployment-first response-signature flow, retain the report verified before inference and require the later `gateway` signature to match its signer and algorithm.

## Continue the flow

Bind the verified Gateway identity to your [TLS connection](/cloud/verification/cloud-api/tls). If your application requires model evidence, also verify the [model attestations](/cloud/verification/cloud-api/model-attestations) before inference. Return to the [verification overview](/cloud/verification) for the complete request lifecycle.
