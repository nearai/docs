title: "Experimental Response Signatures"
description: "Inspect an available direct-model response signature against exact bytes and a matching model report."
---

<Warning>
  A signature lookup can return `404` after a direct completion. Treat a missing signature as unavailable. For production verification, use the [NEAR AI Cloud Gateway flow](/cloud/verification).
</Warning>

Use this experimental flow to inspect the signature over exact bytes for a completion sent directly to a model endpoint.

## Preserve exact request and response bytes

Build the request body once and retain the exact bytes sent by the client. Retain the raw response bytes before parsing JSON or Server-Sent Events.

```text
request_hash  = SHA-256(exact request-body bytes)
response_hash = SHA-256(exact response-body bytes)
```

Hash the original bytes with whitespace, line endings, and stream delimiters intact. The signature covers the uncompressed response body. Request `Accept-Encoding: identity`, or hash the body after your HTTP client decompresses it.

## Fetch and verify the signature

Set `<CHAT_ID>` to the `id` in the completion response whose exact bytes you retained.

```bash
curl --fail-with-body -G 'https://<MODEL_SLUG>.completions.near.ai/v1/signature/<CHAT_ID>' \
  --data-urlencode 'signing_algo=<SIGNING_ALGO>' \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer <YOUR_NEAR_AI_CLOUD_API_KEY>'
```

Set `<SIGNING_ALGO>` to the explicit algorithm used for the matching model attestation.

For `ecdsa`, recover the Ethereum EIP-191 signer from `text` and `signature`, then compare it with `signing_address`. For `ed25519`, verify the UTF-8 bytes of `text` using `signing_address` as the public key. Reject unsupported algorithms.

Then require that `text` is exactly:

```text
<MODEL_ID>:<request_hash>:<response_hash>
```

Take `<MODEL_ID>` from the `model` field in the original Chat request. Use the [manual response-signature helpers](/cloud/verification/reference/response-signature-verification) with that ID, the exact request and response bytes, and the verified model signer selected for routing.

## Match the model signer

Before sending Chat, verify the returned [direct model attestations](/cloud/verification/direct/model-attestation) and retain the signer of the model key selected for the request. The SDK treats a direct receipt as `provider_tee`, checks it against that signer's address and algorithm, and returns all previously verified reports sharing that signer.

`ecdsa` identities are Ethereum-style signing addresses. `ed25519` identities are Ed25519 public-key bytes encoded as hexadecimal. Always compare the identity together with `signing_algo`.
